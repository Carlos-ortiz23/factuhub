# Architecture

## Shape

Modular monolith, single deployable API plus a web client. No microservices:
the specification explicitly rules them out for the MVP, and a reconciliation
engine is far easier to reason about — and to keep correct — when its rules run
in one process with one transactional boundary.

```
Next.js client  ──HTTP──▶  FastAPI (/api/v1)  ──▶  PostgreSQL
                                  │
                                  ├─▶ importers (CSV / XLSX)
                                  ├─▶ integrations (World Office adapter)
                                  ├─▶ reconciliation engine
                                  ├─▶ reports
                                  └─▶ audit trail
```

## Layers inside `backend/app/`

| Layer | Rule it enforces |
| --- | --- |
| `api/` | HTTP concerns only: routing, status codes, auth dependencies. No business rules. |
| `schemas/` | Transport contracts. These may change without touching the domain. |
| `services/` | Use cases. One entry point per user-visible operation, owning its transaction. |
| `models/` | Persistence shape only. No business logic beyond invariants expressible as constraints. |
| `reconciliation/` | The domain: normalisation, matching, grouping, balances. Pure and testable in isolation. |
| `imports/` | File parsing and column mapping. Produces domain objects, never ORM rows directly. |
| `integrations/` | One package per external system, behind a common connector interface. |
| `reports/` | Report assembly and export. Reads through services, never through raw SQL. |
| `audit/` | Append-only trail. Write-only for the rest of the application. |

Dependencies point inwards: `api → services → reconciliation/models`. The domain
never imports FastAPI, and never imports the HTTP layer.

## Decisions and why

### Integer minor units for money

Amounts are stored as integers in the currency's minor unit (COP cents), never
as floating point. Binary floating point cannot represent decimal money exactly,
and an "almost equal" comparison in a reconciliation engine produces silently
wrong balances. Every amount conversion happens once, at the import boundary.

### UUID identifiers

Primary keys are UUIDs generated by the database, so records can be created in
any order and never collide across environments or during a data migration.

### Explicit constraint naming

`app/db/base.py` sets a `MetaData` naming convention. Without it, index and
constraint names depend on SQLAlchemy defaults and migrations stop being
reproducible between a developer's machine and production.

### Application factory, lazy engine

`create_app()` builds the application instead of a module-level instance, and the
engine is created on first use. Importing a module never requires environment
variables or a reachable database, which is what makes the test suite hermetic.

### Two databases, always

Development and test data live in separate PostgreSQL instances with separate
volumes. A test run that drops and recreates schema cannot destroy work in
progress, and the isolation is enforced by infrastructure rather than discipline.

### Sessions, cookies and CSRF

Authentication is a database row, not a signed token. `sessions` stores only the
SHA-256 digest of the token, its deadline, a revocation timestamp and a CSRF
token bound to that session. Every authenticated request therefore re-checks the
deadline, the revocation flag and `users.is_active`, which is what makes
"quitale el acceso" take effect immediately instead of whenever a cookie expires.

Two cookies are issued at login: the session cookie is `HttpOnly` and
`SameSite=Lax`; the CSRF cookie is readable on purpose, because the frontend has
to copy it into `X-CSRF-Token`. State-changing requests must send that header,
and the server compares it against the value stored with the session — a cookie
injected from a sibling subdomain does not match. `SameSite=Lax` also means the
API and the web app must be deployed on the same site (different subdomains are
fine); a truly cross-site frontend would need a different scheme, not a weaker
cookie.

Failed logins are counted per normalised email in `login_throttles`, with the
check and the increment performed as one atomic `INSERT ... ON CONFLICT` plus
`SELECT ... FOR UPDATE`. The row lock is what stops a burst of parallel requests
from all passing the same stale check. The counter lives in PostgreSQL rather
than process memory because a per-worker dictionary would multiply the budget by
the number of instances. The trade-off is deliberate and visible: someone who
knows an address can lock it out for fifteen minutes, which is why the window is
fixed (never sliding) and short.

### Provider credentials at rest

A company's accounting credentials live in `provider_credentials`, one row per
`(organization, provider, mode)`, and never in the environment: the platform's
own token cannot represent which company is asking, and §11.3 asks for the
company's credentials to be encrypted at rest. The column holds a Fernet token
(AES-128-CBC plus an HMAC-SHA256 tag), so a modified ciphertext is rejected
rather than decrypted into plausible garbage.

The key is `CREDENTIALS_ENCRYPTION_KEY`, deliberately separate from
`APP_SECRET_KEY`: rotating sessions must not make stored credentials unreadable,
and rotating credentials must not sign everybody out. The token's plaintext also
records the `(organization_id, provider)` it was created for, so a row copied to
another company fails authentication instead of decrypting the wrong tenant's
credentials. Plaintext exists only between decryption and the adapter call.

The connection status is an observation. Saving credentials marks the row
`untested`; only a real call to the provider moves it to `connected` or `error`,
and the sanitized reason is stored for the company to read. Providers in the
catalogue without an adapter are refused with `409` instead of accepting
credentials nobody will ever use. Responses are built from a model that has no
field capable of holding a credential, and the app's validation handler strips
FastAPI's `input` echo so a rejected payload cannot write the secret into an
error body.

### Imports: the interpretation is explicit

A bank exports `1.234,56`; another exports `1,234.56`. The same characters mean
different amounts, and `01/02/2026` is two different days depending on the
convention. Guessing either one imports wrong money that still looks plausible,
so an import carries a column mapping (header names, not positions) plus an
`ImportOptions` with `date_format`, `decimal_separator`, and — when the file has
a single signed amount and no direction column — `positive_is`.

The reader validates the mapping against the real header before creating a job,
so a typo is one clear `422` instead of a file full of row errors. Amounts are
stored as integer minor units, always positive, with `direction` carrying the
sign: a single signed number would force every reader to remember which sign
means "money in" for a bank versus a ledger account.

Idempotency is keyed by the file's SHA-256 plus a hash of the mapping and
options. Uploading the same bytes with the same interpretation is refused
(`409`); the same file with a corrected interpretation is a new, legitimate
import. Rows are never deduplicated on import: two identical commissions are a
legitimate pair, and duplicate detection belongs to the engine, which can explain
its suspicion instead of silently deleting a movement (§8.5).

Valid rows are imported even when others fail. The job is `completed` when at
least one row was written and `failed` when none was; `rows_read`,
`rows_imported`, the summary and the per-row error table carry the difference,
because a `completed_with_errors` state would be a fifth status the
specification did not ask for.

The original file is stored privately under `IMPORT_STORAGE_DIR`, owner-readable
only, and is never served by a route. Retry reads that original rather than
asking the client to send it again, and only a job that wrote zero rows may be
retried: re-running a partial import would duplicate what already succeeded. The
storage protocol is the seam for the S3-compatible adapter; the local adapter is
what the development and test environments use.

### Reconciliation: a confirmation is reversible, approval is strict

A suggestion is cheap; a confirmation moves money in the accountant's mind. The
confirmation locks the match, the period and the movements, refuses a movement
that someone else already confirmed, and cancels the suggested alternatives that
shared it. Those alternatives are marked with the match that displaced them.

A wrong confirmation must be correctable without a database console.
`POST /matches/{id}/cancel` therefore accepts a confirmed match, sets
`released = true` and makes its movements available again; a human rejection and
an automatic cancellation remain remembered and are not offered afresh. The
period does not need to be reopened for this.

Approval requires zero pending movements, zero statement difference and zero
unexplained difference. The specification forbids approving *unjustified*
differences, which is narrower, but this phase has no justification model and
inventing one before agreeing the convention with an accountant would hide the
gap instead of exposing it.

The Excel export is built from the same summary and movement views as the JSON
route, so the file and the screen cannot disagree. Every text cell is forced to
the `s` data type: a reference or description starting with `=` comes from an
uploaded file and must never become a formula when the workbook is opened.

### Row-level security as a second layer

Multi-tenancy is enforced in the backend on every request. PostgreSQL RLS is an
additional guard against a missed filter, not a replacement for authorization
logic — a missing `WHERE organization_id = ...` must still be a bug that fails
its test.

## Pending by design

Deferred to the phases that own them, deliberately not stubbed here:

- CORS and trusted-host middleware (needed only if the web app stops being
  same-site; the cookie scheme above deliberately assumes it stays same-site).
- MFA for administrators and approvers (§11.1 calls it recommended, not required).
- Password recovery and email delivery.
- Object storage for original files: the local private adapter exists; the
  S3-compatible one and the retention policy belong to the deployment phase.
- Redis/Celery — only if measured volume requires it.
- Centralised logging, monitoring and backups (phase: deployment).
