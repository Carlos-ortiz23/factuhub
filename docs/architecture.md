# Architecture

## Shape

Modular monolith, single deployable API plus a web client. No microservices:
the specification explicitly rules them out for the MVP, and a reconciliation
engine is far easier to reason about — and to keep correct — when its rules run
in one process with one transactional boundary.

```
Next.js client  ──HTTP──▶  FastAPI (/api/v1)  ──▶  PostgreSQL
                                  │
                                  ├─▶ importers (CSV / XLSX)
                                  ├─▶ integrations (World Office adapter)
                                  ├─▶ reconciliation engine
                                  ├─▶ reports
                                  └─▶ audit trail
```

## Layers inside `backend/app/`

| Layer | Rule it enforces |
| --- | --- |
| `api/` | HTTP concerns only: routing, status codes, auth dependencies. No business rules. |
| `schemas/` | Transport contracts. These may change without touching the domain. |
| `services/` | Use cases. One entry point per user-visible operation, owning its transaction. |
| `models/` | Persistence shape only. No business logic beyond invariants expressible as constraints. |
| `reconciliation/` | The domain: normalisation, matching, grouping, balances. Pure and testable in isolation. |
| `imports/` | File parsing and column mapping. Produces domain objects, never ORM rows directly. |
| `integrations/` | One package per external system, behind a common connector interface. |
| `reports/` | Report assembly and export. Reads through services, never through raw SQL. |
| `audit/` | Append-only trail. Write-only for the rest of the application. |

Dependencies point inwards: `api → services → reconciliation/models`. The domain
never imports FastAPI, and never imports the HTTP layer.

## Decisions and why

### Integer minor units for money

Amounts are stored as integers in the currency's minor unit (COP cents), never
as floating point. Binary floating point cannot represent decimal money exactly,
and an "almost equal" comparison in a reconciliation engine produces silently
wrong balances. Every amount conversion happens once, at the import boundary.

### UUID identifiers

Primary keys are UUIDs generated by the database, so records can be created in
any order and never collide across environments or during a data migration.

### Explicit constraint naming

`app/db/base.py` sets a `MetaData` naming convention. Without it, index and
constraint names depend on SQLAlchemy defaults and migrations stop being
reproducible between a developer's machine and production.

### Application factory, lazy engine

`create_app()` builds the application instead of a module-level instance, and the
engine is created on first use. Importing a module never requires environment
variables or a reachable database, which is what makes the test suite hermetic.

### Two databases, always

Development and test data live in separate PostgreSQL instances with separate
volumes. A test run that drops and recreates schema cannot destroy work in
progress, and the isolation is enforced by infrastructure rather than discipline.

### Sessions, cookies and CSRF

Authentication is a database row, not a signed token. `sessions` stores only the
SHA-256 digest of the token, its deadline, a revocation timestamp and a CSRF
token bound to that session. Every authenticated request therefore re-checks the
deadline, the revocation flag and `users.is_active`, which is what makes
"quitale el acceso" take effect immediately instead of whenever a cookie expires.

Two cookies are issued at login: the session cookie is `HttpOnly` and
`SameSite=Lax`; the CSRF cookie is readable on purpose, because the frontend has
to copy it into `X-CSRF-Token`. State-changing requests must send that header,
and the server compares it against the value stored with the session — a cookie
injected from a sibling subdomain does not match. `SameSite=Lax` also means the
API and the web app must be deployed on the same site (different subdomains are
fine); a truly cross-site frontend would need a different scheme, not a weaker
cookie.

Failed logins are counted per normalised email in `login_throttles`, with the
check and the increment performed as one atomic `INSERT ... ON CONFLICT` plus
`SELECT ... FOR UPDATE`. The row lock is what stops a burst of parallel requests
from all passing the same stale check. The counter lives in PostgreSQL rather
than process memory because a per-worker dictionary would multiply the budget by
the number of instances. The trade-off is deliberate and visible: someone who
knows an address can lock it out for fifteen minutes, which is why the window is
fixed (never sliding) and short.

### Row-level security as a second layer

Multi-tenancy is enforced in the backend on every request. PostgreSQL RLS is an
additional guard against a missed filter, not a replacement for authorization
logic — a missing `WHERE organization_id = ...` must still be a bug that fails
its test.

## Pending by design

Deferred to the phases that own them, deliberately not stubbed here:

- CORS and trusted-host middleware (needed only if the web app stops being
  same-site; the cookie scheme above deliberately assumes it stays same-site).
- MFA for administrators and approvers (§11.1 calls it recommended, not required).
- Password recovery and email delivery.
- Object storage for original files (phase: imports).
- Redis/Celery — only if measured volume requires it.
- Centralised logging, monitoring and backups (phase: deployment).
